# 1. What is Redis Server

The **Redis Server** is the main process that:

* Accepts client requests
* Stores data in memory
* Executes Redis commands
* Manages persistence
* Handles replication and clustering

Redis is an **in‑memory key‑value database**, which means data is stored primarily in **RAM**.

This design makes Redis extremely fast.

However, because RAM is **volatile**, Redis provides **persistence mechanisms** to store data on disk.

---

# 2. Redis Server Architecture

Basic workflow:

Client → Redis Server → In‑Memory Data → Response

Redis uses a **single‑threaded event loop** to process commands.

Advantages:

* No locking
* No thread context switching
* Extremely high throughput

Redis can process **100k+ requests per second**.

# 5. Redis Persistence Overview

Redis persistence allows Redis to **store in‑memory data on disk**.

Why?

RAM is **volatile**.

If Redis crashes or restarts, all memory data would be lost.

Redis provides two persistence methods:

1. RDB (Redis Database Snapshots)
2. AOF (Append Only File)

---

# 6. RDB Persistence (Snapshots)

RDB creates **point‑in‑time snapshots** of the dataset.

Snapshots are stored in a binary file:

```
dump.rdb
```

Redis periodically saves snapshots based on configuration rules.

---

## Example

```
SET user:1 "Sayandeep"
SET user:2 "Alex"
```

After snapshot:

```
dump.rdb
```

If Redis restarts:

```
Data restored from dump.rdb
```

---

# 7. RDB Commands

## Trigger Snapshot (Blocking)

```bash
SAVE
```

---

## Trigger Snapshot in Background

```bash
BGSAVE
```

Recommended because it **does not block clients**.

---

## Check Last Snapshot Time

```bash
LASTSAVE
```

Example output

```
(integer) 1712345678
```

---

## Check Persistence Status

```bash
INFO persistence
```

Example

```
rdb_last_save_time:1712345678
rdb_changes_since_last_save:5
```

---

## RDB Configuration

Inside **redis.conf**

```
save 900 1
save 300 10
save 60 10000
```

Meaning

| Condition                   | Action   |
| --------------------------- | -------- |
| 1 change in 900 seconds     | Snapshot |
| 10 changes in 300 seconds   | Snapshot |
| 10000 changes in 60 seconds | Snapshot |

---

# 8. AOF Persistence (Append Only File)

AOF stores **every write command executed by Redis**.

Example logged commands

```
SET user:1 Alex
SET user:2 John
DEL user:1
```

Saved in file

```
appendonly.aof
```

During restart, Redis **replays these commands** to rebuild the dataset.

---

# 9. AOF Commands

## Enable AOF

```bash
CONFIG SET appendonly yes
```

Or inside redis.conf

```
appendonly yes
```

---

## Configure Sync Policy

```
appendfsync always
appendfsync everysec
appendfsync no
```

Recommended setting

```
appendfsync everysec
```

Meaning Redis writes commands to disk **every second**.

---

## Rewrite AOF File

Over time the AOF file grows large.

Rewrite to compress it.

```bash
BGREWRITEAOF
```

Example

Original AOF

```
SET user:1 Alex
SET user:1 John
SET user:1 David
```

Rewritten AOF

```
SET user:1 David
```

---

## Check AOF Status

```bash
INFO persistence
```

Example

```
aof_enabled:1
aof_rewrite_in_progress:0
aof_last_bgrewrite_status:ok
```

| ------------------------- | -------------------------- |

# 13. RDB vs AOF Comparison

| Feature        | RDB       | AOF             |
| -------------- | --------- | --------------- |
| Method         | Snapshot  | Command Log     |
| File           | dump.rdb  | appendonly.aof  |
| Speed          | Very fast | Slightly slower |
| Data Loss      | Possible  | Minimal         |
| File Size      | Small     | Larger          |
| Recovery Speed | Faster    | Slower          |

---

# 14. Production Best Practices

Most production systems use **both persistence methods**.

Example configuration

```
save 900 1
save 300 10
save 60 10000

appendonly yes
appendfsync everysec
```

Benefits

RDB → fast backups

AOF → minimal data loss

# 15. Real‑World Example (ML Systems)

Imagine a **FastAPI ML prediction API** using Redis for caching.


Without persistence

With persistence

```

```
